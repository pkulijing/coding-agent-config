# Shell 脚本开发规则

> 本文档由 `coding-agent-config` 仓库的 `playbooks/shell.md` 提供，经 `install.sh` 共享软链到 `~/.coding-agent/playbooks/shell.md`。修改请回到 `coding-agent-config` 仓库，不要直接编辑软链目标。
>
> **触发条件**：Coding Agent 在本轮任务涉及生成 / 编辑 **bash / shell 脚本**（含**经 ssh / 定时器 / CI 非交互式执行**的脚本），或**向用户给出需要他手动粘贴执行的 shell 命令**时，**必须先把本文件读入上下文**，再开始动手。

本文分三族：**§1–§3、§8 是「注释在 shell 眼里根本不是注释」这一族的固定坑**（§1–§3 由中文 / 全角字符触发，§8 由反引号 / `$(...)` 触发），只在特定字符出现时才踩得上，但一踩就极难归因；**§4–§6、§9–§10 是写脚本的工程实践**，与是否含中文无关；**§7 管的是给人手动执行的命令**，与写脚本无关。

> **本文章节编号只增不改**（仓内多处按号引用本文，如 `scripts/platform_issue.md` 引 §4、`playbooks/scheduled-agent.md` §3.3 引 §5）。故同族的新条目一律**附在末尾**而非插队 —— 读 §1 时请一并看 §8。

Coding Agent 写含中文的 shell 脚本时，反复在「中文 / 全角字符 × shell 引号与变量名」上踩坑——这类 bug 往往**只在真机才暴露**、现象诡异、排查耗时，且与具体业务无关、任何让 Agent 生成中文脚本的项目都可能复现。下面两条钉死。

## 1. 双引号串内的中文注释禁用字面半角双引号 `"`

把远端命令拼成 `run_remote "$host" "<多行 heredoc，含中文注释>"` 这类「双引号包裹的大段脚本」时，若某条中文注释里出现**字面半角双引号** `"`（如 `# …故无"小终端裁小"之虞…`），那个 `"` 会**提前闭合**外层字符串，注释后半段被 shell 当独立 word 拆走 → 函数只收到被截断的前半段命令。

**最阴的地方**：前半段照常执行（如 `new-session` 成功），后半段（`pipe-pane` / `echo` 完成回显）**静默丢失**，现象是「会话建起来了但日志不生成、无完成回显」，极难一眼归因到「一条中文注释里的一个引号」。

**修法**：双引号串内的中文注释一律用中文引号「」，**禁字面半角双引号**；确需则转义 `\"`。

**同族**：**未加引号的 heredoc（`<<EOF`）里的注释同样不是注释** —— 那里的触发字符是反引号与 `$(...)`，见 §8。两条一起记成一句：**凡注释所处的上下文本身会被 shell 解释（双引号串内、未加引号的 heredoc 内），`#` 就挡不住任何东西。**

## 2. `$var` 紧贴 CJK / 全角字符 → 一律 `${var}`

`$var` 后**紧贴**一个 CJK 或全角字符时，Bash 可能把那个字符的**首字节**当成变量名的一部分 → 解析成一个不存在的变量；`set -u` 下直接 abort 报 `unbound variable`。

```sh
echo "OK: ...（SHA=$CURRENT）"   # $CURRENT 紧贴全角 '）' → 报 `CURRENT\xef: unbound variable`
echo ">> $host：建会话"          # $host 紧贴全角 '：' → 报 `host?: unbound variable`
```

**触发条件随 bash 版本与 locale 实现分叉，两侧都可能触发 —— 别去记「哪一侧安全」。** 已实测两台，结论相反：

| 环境 | `LC_ALL=C` | UTF-8 locale |
| --- | --- | --- |
| macOS 自带 bash `3.2.57(1)` | 正常 | **报错** |
| Linux bash `5.2.21(1)` | 正常 | 正常（测的是 `C.UTF-8`，charmap 实为 `UTF-8`；该机无 `en_US.UTF-8`） |

一秒自测本机落在哪一侧：

```console
# ① 先确认要测的 locale 真的生效 —— charmap 得是 UTF-8
$ LC_ALL=en_US.UTF-8 /bin/bash -c 'locale charmap'
# ② 再各跑一次
$ LC_ALL=C           /bin/bash -uc 'V="x"; echo "终止（$V），重试"'
$ LC_ALL=en_US.UTF-8 /bin/bash -uc 'V="x"; echo "终止（$V），重试"'
```

⚠ **第 ① 步不能省，否则这个自测会骗你**：精简容器 / CI 镜像常没装 `en_US.UTF-8`，`setlocale` 失败后**静默回落到 C/POSIX**（只在 stderr 留 warning，stdout 一切照常），于是两条命令实际测的是**同一个 locale 两遍**，却看起来「两侧都正常」。判据看 `locale charmap`：出 `UTF-8` 才算真站在 UTF-8 侧，出 `ANSI_X3.4-1968` 说明已回落 —— 换一个本机确实装了的 UTF-8 locale 再测（`locale -a | grep -i utf` 查，常见是 `C.utf8`）。

⚠ **自测只用来满足好奇，不构成豁免**：修法（下面那条）**与 locale 无关，两侧都成立**，所以不必判断自己在哪一侧，更不能因为「我这里是 UTF-8 / 我这里是 C」就认为不会踩。**按环境判断安全性正是这条坑最主要的危害** —— 写脚本的机器与跑脚本的机器（定时器 / CI / ssh 远端）往往不是同一台，也未必是同一个 bash 版本。

**修法**：

- `$var` 后若紧跟中文 / 非 ASCII 字符，**一律写 `${var}`**——花括号显式界定变量名边界，CJK 字节不再被吞。
- 更稳的做法：**远端 / 拼接执行串里只放 ASCII**，中文进脚本注释、不进执行串；中文 / 全角字符确需紧贴变量时再用 `${var}` 定界。

## 3. 可选自检

落地后想批量自查，可用轻量 grep：扫双引号 heredoc 注释里的字面 `"`、以及 `$word` 紧贴非 ASCII（`\$[A-Za-z_]\w*` 后接 `ord>127` 字符）的位置。但规则文档优先——写脚本时按上面两条直接写对，比事后扫描更省心。

## 4. 只在远端 / CI 跑的脚本，必须配一个本地沙盘测试

**通则**：凡是**只在远端环境执行、且失败代价高**的脚本，都要配一个能在本地真跑起来的沙盘测试。典型属此类的有：CI 脚本、部署脚本、git hook、定时任务的 wrapper。

这类脚本有个共同的糟糕结构：**它们通常是最不该出错的那一批**（碰主分支、碰线上、碰别人的机器），却因为「本地跑不起来」而事实上裸奔——改错了要等真的触发一次才暴露，而那一次的代价就落在 master / 线上了。「本地跑不起来」不是豁免理由，是**必须搭沙盘**的理由。

**沙盘的三个要件**（缺一条都会退化成自我安慰）：

1. **外部依赖用桩替身**：把脚本调用的外部 CLI 换成一个同名 shell 桩——查询类子命令返回预置 JSON，其余子命令记日志后返回成功。桩放在临时目录并前置到 `PATH`。
2. **副作用全部落在临时目录**：每个用例现造环境而非复用真环境。涉及 git 的，`git init --bare` 造一个 origin + 一个 clone，把分支拓扑铺出来。
3. **断言对真实副作用取证，不对日志字符串取证**：查远端 ref 的 SHA、`git rev-list --merges` 的条数、`ls-remote` 里分支是否已删、桩的调用日志里有没有那条命令。断言「脚本打印了什么」几乎没有价值——**打印对了而事情做错了**正是这类脚本最常见的失败形态。

**被测对象是「生成物」时，断言要直接检验下游解析器的要求，别查特征字符串。** 脚本的产出若是一份要被别的程序读的文件（systemd unit、YAML、JSON、ini），断言就该照那个解析器的规矩逐行验——例如 unit 文件「每个非空非注释行必须是 `[Section]` 或含 `=`」。查「输出里有没有某个特征串」挡不住污染：多出来的垃圾行照样通过。§8 那次 heredoc 污染正是这样跑掉的——**5 个 reviewer 全部漏过**，因为 reviewer 审的是脚本文本、不是它生成了什么，只有真跑一次并验生成物才暴露。

**桩与生产在「会不会往 stdout 输出」这个维度上必须同构，否则测试是瞎的。** 同一次踩坑里，第一版桩只把参数记进日志、**不往 stdout 打任何东西**，于是命令替换的结果是空串、污染压根不发生——把出错的写法加回去，测试照样全绿。让桩像真命令那样往 stdout 打几行内容之后，变异才被抓住。**给桩写行为时，先问「真命令在这条路径上会不会有输出」，而不是只问「它会不会被调到」。**

**一个前置条件：测试若要 `source` 生产脚本，必须先给该脚本加好守卫，再写测试跑红。** TDD 的「红 → 绿」正序有个隐含前提——**跑红这件事本身没有副作用**。而当测试靠 `source` 一个可执行脚本来取其中的函数时，这个前提不成立：`source` 会执行该脚本顶层的一切，包括主流程。

本仓踩过一次：给 `install.sh` 加新函数时按正序先写沙盘测试跑红，测试用 `source install.sh` 取被测函数，**而此时守卫还没加**——这次「跑红」把完整安装流程真跑了一遍，还跑歪了：`install.sh` 用 `REPO_DIR="$(cd "$(dirname "$0")" && pwd)"` 推导仓库根，而 **`source` 语境下 `$0` 是调用方脚本**，于是 `REPO_DIR` 被算成了测试脚本所在的目录，两端 `global-repo` 软链被改指过去。**破坏是静默的**——`ln -s` 成功、退出码 0、测试照常输出红态结果；不盯着 install 的日志就发现不了，等到某个依赖该软链的 skill 行为异常时，已经很难联想到是一次跑红造成的。

故这里「**先加隔离、再跑红**」优先于「先跑红、再实现」——因为跑红的代价不再是零。守卫放在主流程段之前：

```sh
if [ "${_LIB_ONLY:-0}" = "1" ] && [ "${BASH_SOURCE[0]}" != "$0" ]; then
    return 0
fi
```

**`[ "${BASH_SOURCE[0]}" != "$0" ]` 这半条不能省**：它把守卫限定在 `source` 语境内。只判环境变量的话，那个变量一旦被意外 export，脚本被**直接执行**时就会撞上「`return` 不在函数、也不在被 source 的脚本里」——bash 报 `return: can only 'return' from a function or sourced script`，然后分两种情况，都不是你想要的：带 `set -e` 时**整个脚本当场挂掉**（退出码非 0，主流程一步没跑）；不带时**报一行错却照样把主流程跑完**。两种的错误信息都与真实病因（一个环境变量泄漏了）毫无关联。

**守卫里必须是 `return` 而不是 `exit`**：`exit 0` 在脚本被 source 时会把**调用方的 shell 一起结束**——测试脚本 source 完就地终止，后面的用例一条都不跑，而且退出码 0、伪装成一次成功运行。反过来，`exit 0` 配上「只判环境变量」的半条守卫，在直接执行时才真会零输出 + 退出码 0 地静默 no-op。**两个坑分属两种写法**，别记混：`return` + 上面那半条守卫，是唯一在两种语境下都正确的组合。

**配套**：被 source 的脚本若在顶层用 `$0` 推导路径（`REPO_DIR="$(cd "$(dirname "$0")" && pwd)"` 这类），守卫挡得住主流程、挡不住守卫之前的推导语句。这类语句要改用 `${BASH_SOURCE[0]}` 取自身路径，否则被 source 时算出来的仍是调用方的目录。

**成本与回报的实证**：本仓 `.github/scripts/ff-merge.sh` 只在 GitHub Actions 里跑，而它干的事是直接 push 默认分支。配的 `.github/scripts/ff-merge.test.sh` 一个文件、两百来行，覆盖四类触发路径。**它当场抓到一个 bug**：`/ff` 评论触发的匹配没剥 `\r`，导致网页端发的多行评论恒不触发——而这正落在原有测试的盲区里（原三例全是 `pull_request_target` 触发，`/ff` 解析路径零覆盖）。

**推论**：写这类脚本时，沙盘测试的覆盖面要按**触发路径**铺，而不是按「主流程跑通了就行」铺。少覆盖一条触发路径，那条路径就是零验证的。

## 5. 非交互式执行（ssh / 定时器 / CI）不继承 profile，PATH 里没有 `~/.local/bin`

**适用场景**：脚本里出现 `ssh <host> '<cmd>'`，或脚本本身由定时器 / CI 拉起，且 cmd 用到任何**用户级安装**的工具——`~/.local/bin`（`uv tool install` / pipx 装的 `lark-cli`、`claude`、`uv`、`glab` 之流）、`~/.cargo/bin`、`~/go/bin`、homebrew 的 `/opt/homebrew/bin`。

**根因**：**非交互式 ssh（`ssh host 'cmd'`）不读 `.bashrc` / `.zshrc` / `.profile`**，PATH 只剩系统默认那几个（以 Ubuntu 为例，各发行版 / macOS 的具体串不同，但一样不含用户级目录）：

```
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin
```

用户级装的工具一个都不在里面。现象是脚本的依赖检查当场报「缺少依赖: xxx 未安装或不在 PATH」，而人 ssh 进那台机器**手敲同一条命令一切正常**。

**为什么这个坑会反复发生**（这条是重点）：**写 ssh 命令的人通常会先手动验证一遍，而手动验证是在交互式 shell 里跑的——恰好绕开了这个失败模式。** 验证方式本身掩盖了问题，于是同一个坑在每个新项目、每个新部署脚本里重来一次，每次都要从「命令明明是对的」重新诊断一遍。

**三种修法，按优先级**：

1. **被调脚本自己 export PATH（治本，首选）**——放在依赖检查 / 首次用到外部命令**之前**：

   ```sh
   export PATH="${HOME}/.local/bin:/opt/homebrew/bin:/usr/local/bin:${PATH}"
   ```

   优点是**不管谁怎么调它都成立**：ssh 调、定时器调、CI 调、人手敲，全都对。实证：某部署仓的 `run_daily.sh` 早就这么写了（定时器同理不继承 profile），而同仓的 `install.sh` 因为此前只被人手敲过，一直没暴露——**同一个仓库、同一类问题，只有被自动化调用过的那个是对的**。

2. **调用方每条 ssh 自带 PATH**：

   ```sh
   ssh "${host}" 'export PATH="${HOME}/.local/bin:${PATH}"; <cmd>'
   ```

   用于 cmd 不是自家脚本、改不了的场合（如直接 `uv run ...`）。缺点是**每条都要记得带**，漏一条就退回原状。

3. **`ssh "${host}" 'bash -lc "<cmd>"'`**（login shell 会读 profile）。看着最省事，但依赖对端 profile 的具体内容，且 login shell 会把 profile 里的一切都跑一遍——包括耗时的初始化与可能污染 stdout 的交互式输出。**最后选。**

⚠️ **修法 2 / 3 的 `<cmd>` 一旦自带引号或 `$`，模板会静默破掉**，两条各有各的破法：

- **修法 2（外层单引号）**：`<cmd>` 里只要出现单引号（`awk '{print $1}'`、`jq '.a'`），就**提前闭合**外层单引号，ssh 的参数边界被打散。与 §1 同一类病。
- **修法 3（`bash -lc "<cmd>"`）**：`<cmd>` 里的 `$` 会在**本地**那层双引号里就被展开，远端收到的是展开后的残骸。实测 `bash -lc "echo test | awk '{print $1}'"` —— `$1` 在本地展开成空，awk 程序退化为 `{print }`（即 `print $0`），**输出恰好和正确结果一模一样**，单看输出根本发现不了。

失败形态是**静默的部分执行**而非报错，这正是本节最忌的那种死法。**所以修法 1 才是首选**：把命令收进被调脚本，调用方那条 ssh 里就只剩一个脚本路径，没有引号可破。

确实要内联时，别硬拼引号，用 stdin 把脚本送过去（参数照常从位置参数传，实测 `$1` / `$2` 取得到）：

```sh
ssh "${host}" 'bash -s' arg1 arg2 < local-script.sh
```

**但这条有个必须知道的前提：`local-script.sh` 自身不能读 stdin**——脚本源码此刻正占着 stdin，脚本里任何 `read` / 等管道输入的循环都会把**自己尚未执行到的后续源码行**当成数据吃掉，然后退出码 0 收场：

```console
$ cat rs.sh
echo "step1"
while read -r l; do echo "got: $l"; done
echo "step2"

$ bash -s < rs.sh
step1
got: echo "step2"     # ← 最后一行没被执行，被自己的 read 当输入吃了
```

脚本需要读输入时，改成先落盘再执行（`scp` 过去或 `cat > 远端路径` 再 `ssh host 'bash 远端路径'`），别用 `bash -s`。

**这个坑的根因不在 ssh，在 bash 本身**：它对脚本源是**边执行边读**的。同一根因还有另一种形态（运行中的脚本被编辑），见 §6。

**与 `playbooks/scheduled-agent.md` §3.3「定时环境的 PATH 极简」是同一根因的两种形态**：那边是 launchd / systemd 拉起的进程，这里是 ssh。**记根因比记形态管用——非交互式执行环境（定时器 / ssh / CI）一律不继承 profile。**

## 6. bash 惰性读取脚本源：运行中的脚本不能编辑

**规则**：一个脚本正在跑（尤其后台长任务），**就别碰它的源文件**——要改先停。

**根因**：bash **不是一次性把脚本载入内存再执行**，而是按**字节偏移边读边执行**：执行到哪读到哪。编辑会改变后续内容的字节位置，于是正在跑的那个进程从一个**错位的偏移**继续解析，把半条语句当成完整语句读。

**失败形态极难归因**——报的是语法错，而脚本语法完全正确：

```console
$ # 一个下载脚本正在后台跑，中途把它里面重复的路径解析逻辑抽了出去
scripts/download_image_models.sh: line 76: unexpected EOF while looking for matching `"'

$ bash -n scripts/download_image_models.sh   # 当场就过，语法没问题
$
```

线索只有「这个脚本刚才被改过」一条，而那通常已是好几步之前的事。**Coding Agent 天然容易踩**：一边让长任务在后台跑、一边继续迭代代码，本来就是很自然的工作方式。实证代价：一次 43 GB 权重下载崩在半路，已下完的 12 GB 白费（崩溃发生在拍平目录之前，分片落在了中间路径上）。

**确需一边跑一边改**：把脚本**连同它所在的整个目录**复制一份到别处跑，**别只复制那一个文件**。单文件复制会让 `source ./sibling.sh` 这类相对路径静默失效——实证：把脚本冻结到 scratchpad 单独跑，它 `source` 的同目录 `_paths.sh` 没跟着走。

**但整目录复制只解决「兄弟文件丢了」这一种失败形态。** 上面那次二次翻车正是栽在第二种上：`_paths.sh` 本身依赖自己位于 git 仓内（`git rev-parse` 一类），复制到仓外照样直接报错。**脚本对自身所处位置有隐式假设时，没有更巧的办法——就是老实停。**

**同族**：§5 末尾 `bash -s < script.sh` 时脚本自身不能读 stdin（`read` 会把自己尚未执行的源码行当输入吃掉）——同一条「流式读取脚本源」的另一种形态。**记根因比记形态管用。**

## 7. 给用户手动执行的命令：长的一律写成脚本，只给一条短命令

**现象**：给用户「你复制这段执行一下」的命令时，若给的是**多行命令块**、或**逻辑上是单行但很长**，用户复制粘贴过去经常直接报错。

**根因**：Coding Agent 的输出在终端里按 markdown 渲染，**超出终端宽度的长行会被软折行**。用户框选复制时，折行处可能被带进真实的换行符，命令就在中间断掉了——而这与命令本身写得对不对无关，纯粹是渲染宽度决定的，同一条命令在宽终端里没事、窄终端里就坏。

**规则**：

- **短命令**（一眼看完、不会折行）→ 直接给，照常。
- **长命令 / 多步命令** → **写进一个短路径脚本**（如 `~/x.sh`），然后只给用户一条命令：

  ```sh
  bash ~/x.sh
  ```

这样用户要复制的永远是一条不会折行的短命令，脚本内容多复杂都不影响粘贴。

**判据**：问自己「这段会不会在用户的终端里折行」——拿不准就写脚本。写脚本的成本是固定的一点点，粘错命令的排查成本却毫无上限（用户看到的是一条语义被截断的命令报出的莫名其妙的错，而你根本不在现场）。

## 8. 未加引号的 heredoc 里，注释也会被 shell 解释

**与 §1 同族**——都是「注释在 shell 眼里根本不是注释」，只是触发字符不同（§1 是 `"`，这里是反引号与 `$(...)`）。

**踩法**：用 heredoc 生成 systemd unit，因为 `${AUTOMATION_DIR}` 需要展开，所以 `EOF` **不能**加引号：

```bash
cat > "${UNIT_DIR}/x.service" <<EOF
[Service]
# 超时后 systemd 判 failed，至少 journal 与 `systemctl --user status` 里留下痕迹
TimeoutStartSec=1800
ExecStart=/bin/bash ${AUTOMATION_DIR}/run.sh
EOF
```

那对反引号**被真的执行了**，整份 `systemctl --user status` 的输出（含完整 cgroup 进程树）原样写进 unit 文件：14 行 → 188 行 / 21KB，systemd 逐行刷 `Missing '=', ignoring line`。

**最阴的地方**：`TimeoutStartSec` 与 `ExecStart` 仍被正确解析（systemd 跳过垃圾行继续往下读），`systemctl start` 照常工作、**退出码 0**。只有主动 `wc -l` 或 `systemd-analyze verify` 才看得出这份文件是脏的——功能没坏，所以没有任何信号告诉你它坏了。

**判据**：凡 `<<EOF` **未加引号**的 heredoc，其中的注释与正文一样受变量展开与命令替换约束。要在这类 heredoc 里写说明，**反引号与 `$(...)` 一律禁用**（引用命令名时用中文引号「」代替）。不需要展开变量的 heredoc，`<<'EOF'` 加上引号即可一次性免疫整类问题——**先问「这份 heredoc 真的需要展开吗」，需要才用不加引号的形态。**

**配套的一条更普遍的教训**：这个 bug **源码 review 看不出来**（reviewer 审的是脚本文本，不是它生成了什么），只有真跑一次并去验生成物才暴露。这正是 §4「只在远端 / CI 跑的脚本必须配本地沙盘测试」的又一个实证——**被测对象是生成物时怎么写断言、桩为什么必须在 stdout 维度同构**，都记在 §4 里。

## 9. `timeout` 的两个坑：不带 `-k` 兜不住，带了 `-k` 也治不了垫片

**坑 1：不带 `-k` 等于没兜住。** `timeout N cmd` 只发**一次** SIGTERM；子进程若忽略或屏蔽它，`timeout` 会跟着一起等到子进程自然退出。实测：

```console
$ time timeout 2 bash -c 'trap "" TERM; sleep 30'
# 实际耗时 30.008s（不是 2s），退出码 124
```

注意退出码仍是 124（超时），**它如实报告了「超时了」，只是没能如实兑现「N 秒后结束」**——只看退出码不看耗时，这个坑查不出来。

**坑 2：但 `-k` 对 shebang 垫片同样无效**——这条更隐蔽。npm 生态里大量 CLI 是 `#!/usr/bin/env node` 的**垫片脚本**，内部用 `execFileSync` 把真正的二进制起成**子进程**。于是 `timeout` 的直接子进程是 node、真正卡在网络上的是**孙子进程**；SIGTERM 一到，没注册 listener 的垫片**立即死亡**，`timeout` 见直接子进程已退出就返回 124，**`-k` 那发 SIGKILL 永远不会发出**，孙子成为孤儿继续跑。实测（node v24.18.0 垫片 + 屏蔽 TERM 的原生桩）：`timeout 3` 在 3.004s 返回 124，而 **20 秒后孤儿仍在往同一个日志文件追加内容**。

**这跟 node 没关系**，凡「自己只 `wait`、把真活起成子进程」的垫片都一样——用 bash 垫片 + 屏蔽 TERM 的子进程同样复现：`timeout -k 1 2` 在 2.006s 返回 124，9 秒后孤儿仍在追加日志。**别按语言记这条，按「被包的东西会不会自己再 fork 一层」记。**

**判据**：用 `timeout` 包外部命令前，先确认被包的是**真二进制还是垫片脚本**：

```sh
head -1 "$(command -v foo)"   # 看有没有 shebang
```

垫片形态下**别把 `timeout` 当兜底**——它给的是「我按时返回了」的假象，不是「那件事真的停了」。真正能收拾孤儿的是**进程组 / cgroup 级的清理**（systemd 的 `KillMode=control-group` 默认就是；手写脚本可 `setsid` + 杀进程组）。

**同族**：定时任务里「超时」这条路本身也会静默失效（systemd `Type=oneshot` 默认不超时 + timer 见 unit 仍 active 就静默略过），见 `playbooks/scheduled-agent.md` §3.8。

## 10. `pkill -f` / `pgrep -f` 会匹配到发起它的那层 shell 自己

**适用场景**：`ssh <host> '... pkill -f <模式> ...'`，或任何把 `pkill -f` / `pgrep -f` **内联**进 `bash -c` / `sh -c` 的写法（定时器、CI、被调脚本里同理）。

**根因**：`-f` 匹配的是**整条命令行**，而执行这条命令的那层 shell，自己的命令行里就原样含着 `<模式>`。`pkill` 只排除**它自己**这一个进程，**不排除它的父 shell** —— 于是模式先打在发起者身上，后面用 `&&` / `;` 串的步骤**一条都不执行**。

**失败形态**：远端 shell 被 SIGTERM 杀掉、没有正常退出状态可回传，ssh 客户端就报 **255** —— 看起来像网络断了、像 ssh 自己的问题，而不像「我那条清理命令把自己杀了」。于是每次都要重新确认远端究竟执行到了哪一步。

**不必有 ssh 也成立**，本地内联同样中招 —— **执行这条命令的那层 shell** 死于 SIGTERM，退出码 128+15 = **143**：

```console
$ bash -c 'echo step1; pkill -f "MARKER"; echo step2'
step1
Terminated
# 退出码 143，step2 没有打印
```

⚠️ **中招的不止「最里面那层 shell」**：凡命令行里含该模式的进程都会被打到，**包括调用链上游的包装 shell**。跑上面这个例子时就实测到：`pkill` 连把整条命令（含脚本正文）内联在自己命令行里的**外层包装 shell 一并杀了**，同一批次里后面的用例整个没跑 —— 此时你在最外层看到的**不是 143 而是别的码**（实测 144），甚至根本来不及看。**排查时别只盯着最里面那一层。**

**修法：模式里插一对方括号，破掉自匹配。**

```sh
pkill -f "foo[.]py"            # 而不是 pkill -f "foo.py"
pgrep -f "bin/tool-nam[e]"     # 而不是 pgrep -f "bin/tool-name"
```

`[e]` 是正则字符组、照样匹配一个 `e`，**目标进程照杀不误**；而发起者自己的命令行里是 `nam[e]` 这几个字符连写、不含 `name`，**匹配不上自己**。与 `ps aux | grep "[f]oo"` 是同一个老招。实测（同一对进程，只换写法）：

```console
$ bash -c 'exec -a MARKER_target sleep 120' &   # 目标存活数: 1
$ bash -c 'echo step1; pkill -f "MARKE[R]_target"; echo step2'
step1
step2                                            # ← 发起者活着，后续步骤照跑
# 退出码 0；杀后目标存活数: 0                     # ← 目标确实被杀掉了
```

**顺带一个本来就该改的理由**：`-f` 的模式是**正则**不是字面量，`foo.py` 里的 `.` 本就是「任意字符」。写成 `foo[.]py` 一举两得 —— 既让点号回归字面量、不再误伤 `fooXpy`，又顺手破掉自匹配。

**另一条路**：先 `pgrep` 拿 pid、再 `kill <pid>`。但 `pgrep -f` 同样匹配自身命令行，**方括号一样不能省** —— 实测不带括号时它返回 `871 873`，其中 873 正是那层 `bash -c` 自己的 `$$`；`kill` 下去是同一个死法。

**判据**：**进程被信号带走（ssh 报 255，本地内联看到 143 或其他非常规码）+ 后续步骤一条都没执行 → 先怀疑是不是杀到了自己**，而不是先查网络或远端服务。别把判据钉死在某个具体退出码上 —— 上游哪一层先中招，决定了你最终看到哪个码。

**同族**：§5 讲的是内联进 ssh 的命令会因**引号**静默破掉，这条是它会因**进程匹配**把自己干掉 —— 同属「内联进 ssh 的那条命令，运行环境和你想的不一样」。两条的首选修法也一致：**把命令收进被调脚本**，调用方那条 ssh 里只留一个脚本路径，模式就不出现在发起者的命令行里了。§9 末尾「真正能收拾孤儿的是进程组 / cgroup 级的清理」管的是**怎么杀干净**，这条管的是**别把自己杀了**。

## 11. 解析外部命令的文本输出前，先固定子进程 locale

**判据**：把外部命令的输出喂给解析器之前，先问「字段名、分隔符、数字或诊断文字会不会跟着 `LANG` 变」。会变或未经核实，就在**启动该子进程时**固定 `LC_ALL=C`，并清空 `LANGUAGE`；不要等输出已经本地化了才补解析分支，也不要修改整个父进程的环境。

**失败形态**：解析器匹配 `Name:` / `Ports:`，实际命令却输出 `名称：` / `端口：`，于是把存在的资源判成不存在。字段名、冒号和空格都可能变；只检查值里仍是英文的部分，发现不了这一层失配。[来源案例 #164](https://github.com/pkulijing/coding-agent-config/issues/164) 中，麦克风探测就是因此静默失效。

**Python 调用写法**：

```python
import os
import subprocess

result = subprocess.run(
    ["pactl", "list", "sources"],
    env={**os.environ, "LC_ALL": "C", "LANGUAGE": ""},
    capture_output=True,
    text=True,
    encoding="utf-8",  # 按命令的实际输出编码选择；固定 locale 不等于输出只有 ASCII
    check=True,
)
```

**标准库 `subprocess.run(..., env=...)` 是整体替换子进程环境，不是向继承环境叠加**，因此要先拷贝 `os.environ` 再覆盖 locale。只传 `{"LC_ALL": "C"}` 会丢掉 `PATH`、`XDG_RUNTIME_DIR` 等运行依赖；音频命令即使找得到程序，也可能因此连不上用户会话的服务。此语义以 [Python subprocess 文档](https://docs.python.org/3/library/subprocess.html#subprocess.run) 为准，别与测试框架的环境覆盖参数混用。

**结构化输出优先，但不能据此省略环境核实**：字段稳定不代表 writer 不受 locale 影响。来源案例还记录了 `pactl 16.1 --format=json` 在本地化字符串上报 `Invalid non-ASCII character: 0xffffffe6`；这是该版本的案例，不能外推为所有 JSON 命令的行为。对已知受影响的命令仍先固定 locale，再解析 JSON；不要把命令失败或解析失败兜成「空结果」。

**配套测试：假命令必须会看 `env`，不能永远吐英文 fixture。**

- 用例内显式设置父环境的 `LANG`、`LC_ALL`、`LANGUAGE`，分别模拟英文和中文环境；同时放入假的 `XDG_RUNTIME_DIR` 等运行依赖。无需安装这些 locale，也不连接真实音频服务。
- 在被测模块实际查找 `subprocess.run` 的位置打桩。桩读取调用传入的 `env`；未传时按父环境处理，**未满足 `LC_ALL=C` 且 `LANGUAGE` 为空时返回本地化字段**，满足时才返回英文 fixture，并断言运行依赖仍在。
- 通过真实的探测 / 解析入口断言两种父环境都能识别资源。删掉 locale 覆盖应使中文场景变红；把环境改成只剩 locale 两项应因丢失运行依赖变红。固定 locale 只稳定机器字段，资源名称等用户文本仍可能含中文，fixture 也要保留这类值。

这把「外部命令如何受环境影响」变成了测试输入，避免英文宿主上的固定 fixture 为本地化缺陷背书；对应宪法「环境是被测行为的输入」的要求。
