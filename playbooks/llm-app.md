# LLM 应用开发规则

**凡是要调用 LLM API 就读本文** —— 含纯文本生成 / 改写 / 翻译 / 摘要，**不限于** function calling 与 agent。§1 管「怎么把调用打通」，**每一种场景都要过**；§2 管「多步任务选哪种形态」，只有做 agent / 任务拆分时才相关；§3 管「LLM 组件怎么写单测」，**只要断言里含「模型会不会这么做」就适用**，与是不是 agent 无关（一次性的「保证吐合法 JSON」同样算）。**Python 侧的通用测试与工程规则见 `playbooks/python.md`，此处只写 LLM 特有的部分。**

## 1. 先把调用打通

**这一节先于一切设计问题**：形态选得再对，调用挂死在那里也没有意义。

本节全部来自同一次真实翻车 —— 接一个 **OpenAI 兼容**的国产模型（阿里云百炼专属部署，路径 `.../compatible-mode/v1`）做中文改写，**手搓了 HTTP 调用**（stdlib `urllib`，自写重试 / 退避 / 响应解析）。根因其实很简单（**该模型思考模式默认开启**），但手搓让它变成了一个近一小时都没查出来的黑盒：

| 事件 | 耗时 |
| --- | --- |
| 首次真实运行 | **9 分 06 秒**后失败 `read operation timed out`（3 次重试 × 180s） |
| 单块直调、超时放到 900s | 撞**当次**外部执行上限（10 分钟）被杀 |
| 单块 + 关思考（仍手搓 `urllib`） | 撞**当次**外部执行上限（5 分钟）被杀，**结论无效** |
| 换官方 SDK + 流式探针 | **1 次、170 秒**就定位到根因 |

> 两次撞到的外部上限并不相同（10 / 5 分钟），源记录未说明原因，**此处按原样记** —— 别据此推断存在某个固定的外部超时值。
>
> 这张表要看的是**四行各自失败在哪一层**：第 1 行是自己配的 socket 超时**真的触发了**（还触发了 3 次），可它拦不住总耗时一路拖到 9 分 06 秒；第 2、3 行是**外部上限**先把进程杀了，自己放宽到的 900s 根本没轮到；最后一行换 SDK 后一次就成。**没有任何一次是「我设的整次请求时限生效了」—— 因为手搓 `urllib` 时那个东西压根不存在。**

### 1.1 禁止手搓 LLM HTTP 调用，一律用官方 SDK

**判据不是「这个请求简单不简单」** —— 上面那次要发的就是一个最普通的 chat completion。手搓具体让四件事变糟：

1. **超时语义会被想当然。** `urllib` 的 `timeout` 是**每次阻塞 socket 操作**的超时，不是整次请求的时限 —— 服务端断续吐数据就会不断把它刷新掉。于是「我明明设了超时」的调用，要么在每次 read 上反复触发它却拦不住总时长、要么一路挂到被外部上限杀掉 —— **我以为设的是「整次请求最多跑多久」，实际设的是「每次 read 最多等多久」**。SDK（httpx）也有分层超时，但它的超时与 `max_retries` 是**显式的、有文档的**，不必自己从 socket 语义往上推。
   ⚠️ **更值得记的是这条的复发形态**：同一个项目上一轮的 `SUMMARY.md` 里**已经写过**「`urllib_transport` 只有 per-socket 超时、无整次请求总时限」，写第二个 HTTP 客户端时仍然没联想到。**手搓一次就要重踩一次**，这正是它的成本形态 —— 不是一次性的学习曲线。
2. **非标准参数无从下手。** 供应商的开关（如控制思考模式的那个参数）不在 OpenAI 标准字段里，官方文档给的用法是 SDK 的透传口；手搓 HTTP 时连「该往哪儿塞」这个词汇都没有，只能猜请求体层级。
3. **流式要自己先实现一遍 SSE。** 而流式恰恰是**唯一能把「黑盒挂死」变成可观测**的手段（见 1.4）—— 为了做这个诊断还得先写一个 SSE 解析器，于是诊断本身被推迟。
4. **重试 / 错误类型 / 响应校验全要自己写一遍**，写完还要为它们补一整套测试。换 SDK 后这些代码**整段删掉**。

### 1.2 动手前先确认走哪个兼容层

三选一：**OpenAI 兼容 / Anthropic 兼容 / 供应商原生 SDK**。

> **判据是 endpoint 路径与官方文档，不是模型名。** 国产模型走 OpenAI 兼容是常态 —— 上面那次的路径里就明写着 `compatible-mode`。**选错 SDK 会一路错到参数名与返回结构**，且错得不响亮：很多字段名恰好重合，于是前几个字段都对、偏偏在你真正需要的那个开关上对不上。

### 1.3 非标准参数走 SDK 的透传口，且默认值必须查文档确认

- OpenAI SDK 的透传口是 **`extra_body`**（其内容原样并进请求 JSON body）。别为了一个非标准字段就退回手搓。
- **thinking / reasoning 模式的默认值必须显式确认，不许假设「默认关」。** 它同时影响**延迟**与**费用**（思维链按输出 token 计费），而默认值**各家不同、同一家不同模型也不同**。

实测（同一块 1022 词输入，同一模型）：

| | 耗时 | 思维链 | 正文 |
| --- | --- | --- | --- |
| 默认（思考开） | 170s 仍未结束 | 19,399 字符 | **0 字符** |
| 关掉思考 | **20 秒** | 无 | 1,958 字符 |

**「170 秒吐了 19399 个字符却一个正文字都没有」正是超时的真身** —— 请求既没挂死也没排队，它在认真工作，只是在做你不需要的那件事。

> ⚠️ **两条尚未回官方文档原文核对，故本节不写死**：
> - **①** 关思考的那个参数在**阿里云**侧的确切名称与位置 —— 本次实测用 `extra_body={"enable_thinking": False}` 生效，属**实测**而非文档核对。
> - **②** 传闻「部分模型开启思考时强制流式」。
>
> **两条各自找过哪里、各自什么结果**（按 `GLOBAL_AGENTS.md`「引用外部权威材料」条的留痕门槛**逐条**记 —— 一次尝试不能替两条断言背书）：
> - **①**：抓 `https://help.aliyun.com/zh/model-studio/deep-thinking`，被网络出口代理拒绝（`EGRESS_BLOCKED: Access to help.aliyun.com is blocked`），未取到原文。
> - **②**：另就「开启思考时是否强制流式」搜过一次，返回的仍是指向同一批 `help.aliyun.com` 页面的**搜索摘要**，且摘要**自相矛盾**（一处称流式与非流式都支持、只是推荐流式以免超时，另一处称深度思考下多数模型仅支持流式）。原文同样未取到。
>
> **两条都只剩搜索摘要**，按该条「不许用搜索摘要冒充原文」故均未写进正文。**要按它们写代码之前，先取回官方文档原文核对**，别照抄本节。

### 1.4 首次接入必做一次流式探针

**量三件事**：① 首字延迟；② 第一个数据块落在**思维链字段还是正文字段**；③ 吐字速度。

**它是把「黑盒挂死」变成可观测的最短路径。** 上面那次换 SDK 后一次探针就看到「首字 1.3 秒到达、但第一个数据块是思维链」 —— **这一条同时排除了排队慢、吞吐慢、请求挂死三种猜测**，而在此之前的近一小时里，这三种猜测一个都排除不掉。

### 1.5 别拿 hello world 当连通性验证

**首次验证必须用真实尺寸的输入。**

上面那次「回复两个字」秒回、真实尺寸的块要十几分钟 —— 两者走的是**完全不同的代码路径**（思考模式在短问答上几乎不触发）。一个绿的 hello world 在这里提供的保障是零，还会把你的注意力从「模型在想什么」引开。

## 2. 先选形态：「多步 Agent」还是「一次性任务拆分」

**接 LLM 之前先想清楚这一件事，它决定了返回结构长什么样。两者形态完全不同，混用会静默漏步。**

| | 多步 Agent | 一次性任务拆分 |
| --- | --- | --- |
| 有没有第二轮对话 | **有**：模型返回 tool_call → 系统执行 → 结果**回传**给模型 → 模型据此决定下一步 | **没有**：系统不回传任何执行结果 |
| 「一次只返回第一个 tool_call 然后等」 | **正确行为**，不是缺陷 | **致命**：模型在等一个永远不会来的结果 |
| 该用的返回结构 | 多个 tool_call，逐个执行回传 | **单个 tool + `steps` 数组**，「一次列全」成为参数的语义要求 |

**错配的形态是：系统不回传结果，却仍要求模型「返回 tool_call」。** 那个动作形态正是 agent loop 的第一拍，模型会按训练先验只返回第一步然后等——而它永远等不到。

> 「回传」的具体形态**随 provider 而异，别照字面抄**：OpenAI Chat Completions（及 deepseek / qwen 等兼容协议）用 `role: "tool"` 消息；Anthropic Messages API 没有 `role:tool`，用的是 `role: "user"` 里的 `tool_result` content block。本节讲的是**形态选择**，与具体协议无关。

### 为什么这个坑值得单开一节：症状极具迷惑性

- **有依赖的请求才翻车，无依赖的照常成功**。真实案例：「建 GitLab 账号 + 加入两个组」（后两步依赖第一步）只执行了建号；而「同时加入两个组」（彼此无依赖）100% 正常。
- 表现为「时好时坏、冷不丁坏一次」，**漏掉的那一步不留任何痕迹**——确认卡片正常渲染、执行成功、日志记 info。**人只能看见清单上有什么，看不见缺什么。**

### 实测：这是模型的稳定策略，不是采样噪声

每格 20 次，复用生产 prompt 与 schema：

| 形态 | deepseek-v4-flash | qwen3.7-max |
| --- | --- | --- |
| 多 tool_call（错配） | 5% | 75% |
| 单 tool + `steps` 清单 | **95%** | **100%** |

两条推论，都是实测出来的：

- **调参救不了**：在错配形态下调 `parallel_tool_calls=True` / `temperature=0`（各单开、再双开），三种配置的符合率始终贴地 —— 5% / 5% / 0%。（源数据未标注这三个值属哪个模型；数值与表中 deepseek 的 5% 错配基线一致，应为 deepseek。）
  ⚠️ 这组数据只够证明「调参没把错配救回来」，**不足以证明这两个参数本身无效** —— `parallel_tool_calls` 在 OpenAI 兼容 API 上**默认就是 true**，显式设 true 等于什么都没改。真要归因到参数，得先确认它改变了默认行为。
- **只改 prompt 措辞而不改返回结构，救不回来**：把角色重设为「任务拆解器」但仍走多 tool 通道 → deepseek 5% → 15%、qwen 75% → 35%，两个模型都**远达不到**换结构后的 95% / 100%，且过半数直接退化成纯文本回复。**角色描述与返回结构必须一致**，否则模型在「拆解」与「调用」之间摇摆。
  > 源数据把这一格记作「两个模型都大幅退化」，但按同表的错配基线（5% / 75%）核对，deepseek 实为小幅上升、只有 qwen 退化。**结论「改措辞不能替代改结构」不受影响**，此处按数字如实记；要引用「退化」这个说法请先回源核对。

## 3. LLM 组件的单测必须是统计性的，且不能用 fake 替模型作答

**判据：凡是「模型会不会这么做」的断言，跑一次 assert 通过不提供任何保障。** 必须跑 N 次看符合率，并把用例固化成可重复的基准脚本。

反面样本来自上一节那个项目：改造前的复合请求单测**全绿**——它用 fake 直接构造了两个 `tool_calls`，测的是「给了多个我收不收得全」，恰好绕开「模型给不给」这个唯一的真问题。

> 与 `playbooks/python.md` §4「声明式 schema + 自然语言 prompt 双写处必须加结构性防漂移测试」同族：那条管 schema 与 prompt 之间的漂移，这条管「模型行为」这个断言对象本身。两条都指向同一个失败模式——**用 fake 替模型作答的单测，测的是自己的假设，不是模型**。

## 4. Agent 指令变更必须验证当前会话实际生效

**磁盘定义已更新、服务重启成功，都不能单独证明已有会话已使用新提示词。** 验收要区分三层：磁盘上的角色定义（如 SOUL 文件）、运行时加载的配置、当前会话实际使用的系统提示词或指令版本。

来源 issue #178 记录了 infra-team 首次部署的案例：角色文件修改并重启后，已有会话仍持久化着旧系统提示词，派工后的真实回交没有按新协议完成；相关成员使用框架原生的新建会话能力后，真人交互才完成派工、回交与最终汇总。**这是来源案例，不代表所有框架的会话语义；保留历史与提示词也可能是有意设计，不能直接判为框架缺陷。**

指令变更后的验证顺序：

1. **先查原生机制**：核对所用框架的文档、源码或实际会话状态，确认角色定义何时加载、已有会话是否缓存提示词，以及提供了哪些更新能力，不凭重启结果推断。
2. **取实际会话的证据**：通过原生会话检查能力或实际请求构造路径，核对目标会话使用的指令版本、哈希或必要的脱敏匹配结果；只有磁盘文件的哈希不算会话生效证据。无法检查时明确记为未核实。
3. **按框架能力应用变更**：若旧会话仍使用旧指令，选择框架支持的新建会话、重新加载或其他原生迁移机制，并核对历史保留与迁移代价；不强制所有框架重建会话，不擅自删除会话历史。应用后再次核对目标会话。
4. **用实际交互验收协议**：在目标会话执行一个能区分新旧协议的场景，检查真实动作及其结果。团队 Agent 场景应核对派工、实际回交与最终汇总，不能只看模型声称已遵守协议，也不能以服务重启或配置加载成功代替验收。

**公共验证产物只保留版本、哈希、必要的脱敏匹配结果与验收结论**，不写入私密提示词或会话原文；取证也遵守目标系统的访问权限，避免为证明生效而泄露角色配置或用户内容。
