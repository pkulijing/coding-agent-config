# design 的工作树与归档生命周期

本文件是 `/design` 的 Git 操作细则，CC / Codex 共用。§1 在定位或创建前读；§2–§4 在归档或收尾前读。不适用于普通开发轮压缩，也不授权批量整理其他主题或项目。

## 1. 定位、建立与恢复主题工作树

### 先查主题，再写文档

1. 明确当前仓库、主 checkout、主分支：用 `git worktree list --porcelain` 定位工作树；主分支优先取 `refs/remotes/origin/HEAD` 并仅去掉 `origin/` 前缀，不存在则核对本地 main/master；仍不明确才问人。当前位于开发 worktree 不妨碍定位兄弟主题工作树；所有 git 调用显式 `-C <绝对路径>`。
2. 有 origin 则先用 `git ls-remote --heads origin` 列全远端分支，再 fetch 获取主线与候选主题。**默认 fetch refspec 可能只取 main**（如 single-branch clone），不能把 `refs/remotes/` 的空结果当作远端没有主题；对尚未取回的候选显式 fetch 对应 ref 后再读树。其他已配置 remote 同样列全 heads、核对候选。失败时报告「远端主题未核对」，可继续读取已明确定位的本地主题；**新建主题或改写已有归档前须补齐核对**，不把过期 remote-tracking 当作未发布的证据。无 remote 的纯本地仓无需此检查。
3. 汇总各工作树实际存在的 `docs/design/*/`（含未跟踪文档），以及本地 heads / 远端 refs 的同路径目录，用 `git ls-tree` / `git show <ref>:<path>` 读取。不能只查 `design-*` 分支名：旧主题可能在 master、round 分支或自定义分支上。backup tag 仅作恢复证据，不作为第二个活跃主题。查找和比较使用精确路径；处理含中文、空格的路径时用 NUL 输出或可靠参数边界，不能按空格拆 `worktree` 路径。
4. 按中文主题目录匹配，展示候选状态、工作树、分支与提交。相同主题在主线及主题分支都有时，对比祖先关系与文件内容，区分已集成快照和仍在推进的主题分支；**多个不同版本或多个独立分支均在推进时先让用户选择，不自动挑最新时间戳**。主树看不到文档不是新建依据。

### 新建与恢复

- **新主题**：确认各源都无同名主题，才从已核实的最新主线基线建立 `.worktrees/design-<ascii短名>/`、分支 `codex/design-<ascii短名>`。短名用 `[a-z0-9-]`、2–4 词且不超过 20 字符，不使用 round 编号。用原生 `git worktree add --no-track -b <分支> <绝对路径> <基线>`，避免把主线误设为主题的 upstream。复用已有 `.worktrees/.gitignore`；缺失时按 `/start` 的 worktree 规则建立目录级忽略，不覆盖原规则。
- **唯一的活跃主题工作树**：复用它；若含无关改动或暂存内容，不移动、不 stash、不提交那些内容，停止写入并说明需先隔离什么。主题归档只修改本主题路径，其他已有资产不会因此自动获得提交授权。
- **仅本地主题分支存在**：核验其文件与提交范围后，在 `.worktrees/` 恢复原分支的工作树，不从主线另起空分支。若分支已被另一工作树占用，直接定位过去，不用 `--force` 二次 checkout。
- **仅远端主题分支存在**：fetch 后核验该分支，创建跟踪它的本地同名分支及工作树；若 remote 的窄 refspec 不覆盖它，为此分支追加精确 fetch 映射再建立跟踪，不覆盖用户其他映射。仅手动 fetch 到 remote-tracking 名字下并不足以让 `--track` 识别它。恢复已推送历史不表示获得改写它的授权。
- **只有旧主线或开发分支中的主题**：先读 §2 的历史分类；不要直接在原树续写。已提交文档可从所属分支建立隔离树作只读核对，整理与续写须先确定历史策略。对主树未提交的旧主题，列出两文档、获授权资产、暂存状态，确认迁移清单后再定向复制、核对字节及暂存差异并移除源副本；源文件未安全保全前不删除，其他路径及其暂存状态保持不变。

路径或分支名已占用而归属不明、工作树不可达、主题只剩 backup 证据时，报告候选并保全现状，不删目录、不 prune、不加后缀悄悄分叉同主题。工作树建立后告知绝对路径与分支；所有后续编辑、git 与委派都锚定该树，不能靠跨工具 `cd`。

## 2. 主题单提交归档

### 识别与授权

- 主题稳定标识是目录的精确仓库相对路径。新归档 message 带 `Design-Topic: docs/design/<主题>` trailer；它定位候选，**仍须用实际提交的全部路径验证**。不保存 SHA 到本地状态文件；旧提交无 trailer 时按路径历史查候选，不能单凭标题或 `git log -- <路径>` 的结果判断提交只改过该主题。
- 核对主题分支相对基线的**全部提交**，含每个提交的全部变更路径、父提交与 message；核对各 worktree、其他 heads 和远端 refs 对待改写提交及后继链的引用。备份 tag 可以保留旧链；其他活跃引用不能忽略。
- 有远端时先成功 fetch，并核实待改写提交是否在任一远端分支可达；还要查已知的远端 tag / 其他已发布引用。曾发布后远端删分支、或无法判断发布状态的历史，不能仅凭「当前查不到」宣称从未发布，按需授权处理。
- 使用 `/design` 已授权在独立主题分支创建首个归档，并持续 amend **未发布、未集成、未被其他活跃分支共享且归属明确的单个 HEAD**。每次照常告知结果；这不授权改写其他提交、已发布/集成历史或修改别人的引用。此特殊默认值同步于全局宪法，普通 `/commit` 仍默认新增提交。

### 日常归档：首个 commit / 后续 amend

1. 查看主题树的 `status`、未暂存与已暂存 diff、未跟踪文件。允许集合仅为本主题 `DISCUSSION.md`、`DESIGN.md` 和**获授权的具体 assets 文件**（含删除）；核对真实路径，不跟随越出主题目录的软链。
2. **先核对整个 index，再定向 add，再复核整个 index**；任何无关项都停止，不清空他人的 index、不把它们代提交。未跟踪的资产单独检查，不用 `git add .` / `-A` 或只靠路径限定的 commit 掩盖夹带。无内容和 message 变化则不制造提交。
3. 将主题路径、允许文件清单、已核实归档 SHA（首次为无）、发布/引用检查结论传给 `/commit` 的 design 归档入口。review 与 lint 沿用 `/commit`，若修复产生范围外文件必须重新核对，不自动扩大白名单。
4. 首次创建普通提交；已有且唯一的主题提交**必须恰为 HEAD**，确认单父、未混入其他工作后才 `commit --amend`。最终标题和正文描述当前方案，保留 `Design-Topic`，合并去重已有署名并追加实际执行 Agent 的 `Co-authored-by`；不能以 `--no-edit` 保留旧 Agent 而漏掉当前执行者。
5. 提交后核对主题只占一个提交、提交全部路径属于允许集合，文件与 index 状态符合预期。报告分支、新 SHA 与本地/远端同步状态；尚有未归档资产须明确指出。

### 旧碎片、交错提交与异常拓扑

**HEAD 属于其他工作、多个主题提交、混合范围提交、merge commit、共享引用或已集成历史都禁止直接 amend HEAD。** 先列出本主题提交、其他提交、发布状态与受影响引用，给出具体整理方案并取得对应授权；不得只因用户要单提交就把整段历史 squash。

对已授权、未发布且归属清楚的线性历史：

1. 记录旧 tip、基线、最终 tree、其他提交 message 和补丁；在改写前打 `backup/<分支名>-<时间>` tag。工作树/index 必须干净；有未提交主题更新时，先在独立临时目录保存原字节、删除清单与资产并校验，**确认保全方式后**再整理，不用 hard reset 丢弃，也不建立多余主题快照提交。
2. 在临时分支/工作树整理，不在主 checkout 原地试错。逐个核实主题提交仅改允许路径，且其他提交没有与主题相互依赖；可用原生交互 rebase 将其他提交按原顺序保留，再将本主题提交集中 fixup 为一个，并将已保存的新主题文档应用到它。存在跨主题依赖、混合提交或 merge 拓扑时另提拆分方案，不套这条简单重排路径。
3. 比较最终 tree（无新更新时必须与旧 tip 完全相等；有更新时只允许已确认的主题差异）、其他提交的完整说明和 patch-id/range-diff。冲突、空提交或补丁变化必须解释并确认，不盲选 ours/theirs、不静默 skip。
4. 验证通过后，核对原分支 tip 仍为旧值，再在其干净工作树切换到已验证的新链；不在分支仍被另一工作树使用时直接 update-ref。其他活跃引用的迁移须分别明确授权；原历史和备份保留，临时工作树只在文件已保全后清理。

无法在当前授权内收敛时，把最新文档保留在主题工作树并报告阻塞，不追加同主题快照作为退路，也不把「还没归档」报成完成。

## 3. 远端同步与已发布历史

本地存档本身不授权 push。用户已明确授权的远端与分支可在该范围内同步；没授权则提供具体同步方案。跨设备续聊须文档已在可访问远端，而不只是本地 commit。

- **第一次发布主题分支**：核对远端目标无冲突，用普通 push，只推本主题分支，不推主线或 backup tag。
- **待改写提交已发布**：amend / rebase **之前**说明旧 SHA、后继链影响、受影响引用与同步方式，取得覆盖本地改写及远端替换的授权；已有明确的同主题持续授权可复用，不能将一次普通 push 授权解释为长期强推授权。无授权时可继续写文档，但归档保持待处理，不改写旧提交。
- **远端替换**：取得授权后，先读取并记住该远端主题 ref 的实际 SHA，核对与本地旧链对应，再用带精确 ref 和预期 SHA 的 `--force-with-lease=<ref>:<已核实SHA>`，只更新该主题 ref。不用裸 `--force`、不只依赖可能被后台 fetch 更新的隐式 lease。
- lease 失败或发现远端有其他更新：保全两边历史与本地文档，重新呈现差异和方案，不能循环 fetch 后换 lease 强推。网络失败时报告「本地已归档、远端未同步」，不删除工作树。

## 4. 定稿、搁置、合入与清理

讨论中只存档主题分支，保留工作树，不反复合入主线。定稿/搁置时按以下顺序收尾；不调用开发轮 `/finish`，不写 SUMMARY、不改 DEVTREE、不拆 issue。

1. 更新状态、日期及讨论记录，完成 §2 的最终单提交归档；若归档受阻，到此保全现场。定稿/搁置表示可执行以下本地收尾，不自动授权任何远端写入。
2. 核对最新主线、主 checkout 及其 index 干净（含未跟踪文件）、主题工作树干净，主题相对主线只包含该主题一个提交和允许路径。主树有无关内容时不 stash、不切分支、不 reset；保留主题工作树，报告待合入。
3. 主线前进时先按 §2 核查发布与共享状态，打备份 tag 后在主题工作树 rebase 到主线；冲突或关键假设不成立则暂停，保留/恢复已核实的备份，说明下一步。发布过的主题若缺改写授权，不能因「只是收尾」绕过 §3。
4. 在**主 checkout 已处于目标主分支**且 tip 未变化时 `merge --ff-only <主题分支>`；FF 不可行就停止，不自动生成 merge commit。核对最终主题文档、主题提交祖先关系和主树状态，报告合入结果与未推送状态。
5. **清理单独核验授权**：若已有「合入并清理」或等效授权，核对文件已在目标分支保全、主题提交可达、工作树/index 干净、无忽略或未跟踪资产及其他会话正在使用，再用普通 `git worktree remove` 和安全分支删除（在目标主分支上下文 `branch -d`）。缺清理授权则保留并告知。禁用强制移除；不自动删除 backup tag 或远端分支。

**已集成主题重开**：先读取原方案与 Git 历史，报告维持全生命周期单提交会影响主线及其后继提交；提出明确的历史改写方案并等待授权。若用户选择把重开视为新一版，须明确其对单提交目标的例外；不自行新增同主题第二个提交，也不自动改写主线。
