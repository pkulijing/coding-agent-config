用户调用此 skill 表示手上有一段**还不清晰的背景**，想和你在讨论中逐步收敛出一个方案。**方案本身就是这一轮的最终产出** —— 它可能很宏观、未必落到可执行计划，以后可能拆成很多轮 `/start` 去做，也可能不做。

与现有开发流的分工：

| 入口 | 前提 | 产出 |
| --- | --- | --- |
| **`/design`** | 需求模糊，要讨论才知道做什么 | `docs/design/<主题>/` 下的讨论记录 + 方案 |
| `/start` → `/finish` | 需求明确，要开发 | `docs/<N>-*/` 三件套 + 代码 |
| `/quick` | 小改，一句话说得清 | 仅 commit |

**默认隔离**：每个主题在项目 `.worktrees/` 下使用独立分支与工作树，讨论期间维护同主题一个归档提交。**定位或创建工作树之前必读** [references/git-lifecycle.md](references/git-lifecycle.md) §1；**首次归档、续次存档、合入或清理之前必读**该文件 §2–§4。资源统一从 `~/.coding-agent/skills/design/` 读取。

**明确不做**：不占开发轮次、不启动开发执行计划模式（CC 的原生计划工具不用于本形态；Codex 按讨论记录推进，无需切换模式）、不改业务代码、不拆 issue、不碰 `docs/DEVTREE.md`、不写 `SUMMARY.md`。主工作树的无关内容和暂存区保持原样。

## 参数

| 形态 | 行为 |
| --- | --- |
| `/design <背景描述>` | 新开一份讨论（见「开场」） |
| `/design --resume <主题>` | 跨工作树与分支定位已有讨论（见「续聊」）；主题目录名模糊匹配，命中多个让用户选，无匹配则列出现有讨论 |
| 无参数 | 按 reference §1 汇总各树与分支中的主题、状态与所在分支，问用户新开还是续聊；无主题则追问背景描述 |

## 开场

1. 从背景描述提炼简短**中文主题**，落点 `docs/design/<主题>/`（目录名**不带编号**）。先按 reference §1 查各树与分支；已存在则确认续聊或换主题，绝不覆盖。全库确无该主题才创建主题工作树，告知绝对路径与分支名。
2. **在主题工作树先落盘再提问**：写 `DISCUSSION.md` 的阶段 0（用户原始背景**原样保留**）和 `DESIGN.md` 骨架（状态 `讨论中`，各节暂空或写「待讨论」）。定位或恢复有歧义时先保全现场，不在当前主树兜底写文件。
3. 复述你对背景的理解（一两句），抛出第一轮问题。

## 讨论方法

- **阶段推进**：问题定义 → 约束与前提 → 方案空间 → 取舍 → 收敛成方案。这是默认路线而非死流程，可跳、可回退；**每个阶段收束时向用户确认一次**再往下走。
- **每轮只抛 1–2 个关键问题，每个都附你的建议与理由。** 不做开放式盘问，也不一次列一长串待确认项。用户说「听你的」就按建议定，照样记为决策。
- **引导，但不替人拍板**：方向性的取舍给出推荐并说明代价，由用户决定。
- **分清事实与判断**：能读代码、查资料确认的自己去查（**只读**），别拿来问用户；查不到、或属于「只有人知道」的参数（宪法·计划段）问人，不得猜。涉及外部权威材料的断言遵循宪法「先取原文」。
- **只在本主题工作树写 `docs/design/<主题>/` 下的两份文件**（获授权的配图可放 `assets/`），不改业务代码或其他文档。讨论中冒出「顺手改一下」的冲动，记进 `DESIGN.md` 的开放问题或后续路线，不动手。

## `DISCUSSION.md`：历史，只追加

```markdown
# <主题> · 讨论记录

## 阶段 0：背景输入（YYYY-MM-DD）

<用户原话，原样保留>

## 阶段 1：<议题>（YYYY-MM-DD）

- **输入**：用户提供的信息、约束、偏好
- **分析**：你的观点与判断，附依据（代码 `file:line`、查到的资料、推理）
- **决策**：用户拍板了什么，关键处引用用户原话
- **否决**：被放弃的选项及理由
```

- **写入时机**：用户每做一个关键决策、或一个阶段收束时**立即追加**，不等收尾 —— 长讨论会被上下文压缩，等到最后再整理恰好最容易失真；这份记录也是 `--resume` 的依据。
- **整理而非逐字**：除阶段 0 外不贴对话原文；一个阶段可含多个议题，各自按四项写。某项确实为空就省略该项。
- **用户推翻先前决策也是决策**，新开一段记下来（「推翻阶段 2 的 X，因为……」），不回头改旧段。这与宪法「自己写错自己改、不留痕」不冲突 —— 那条管你自己的笔误（照常直接改），这里记的是用户的方向变化。

## `DESIGN.md`：快照，始终反映当前共识

```markdown
# <主题>

> 状态：讨论中
> 创建：YYYY-MM-DD · 更新：YYYY-MM-DD

## 目标与非目标
## 核心判断
## 方案框架
## 分阶段路线
## 开放问题
```

- 状态取值：`讨论中` / `已定稿` / `已搁置`；`已搁置` 时在状态行下补一行原因。
- 章节是建议骨架，**按主题增删**（「分阶段路线」对纯宏观讨论可以没有）；**不要求落到可执行粒度**。
- 随讨论**整体改写**以反映当前共识，不追加历史 —— 历史在 `DISCUSSION.md`。每个阶段收束后同步更新一次，并刷新「更新」日期。
- 读者只读这一份也要能看懂方案：写结论与理由，不写「见讨论记录阶段 3」式的跳转。

## 续聊（`--resume`）

1. 先按 reference §1 定位并复用或恢复主题工作树；不能只因当前树看不到文档就另建一份。读该树的 `DESIGN.md` 与 `DISCUSSION.md`，按 §2 核对归档提交与发布状态。已合入主线的主题重开须先按 §4 确定历史策略，再修改文件。
2. 向用户复述：当前共识（几句话）、开放问题、上次停在哪个阶段。
3. 在 `DISCUSSION.md` 新开一个带当天日期的阶段，从开放问题继续。
4. 若重开的是 `已定稿` / `已搁置` 的方案，状态改回 `讨论中`。

## 存档与收尾

| 时机 | 做法 |
| --- | --- |
| 一次会话要结束、讨论未完 | 对齐两份文件，按 reference §2 调 `/commit` 的 design 归档入口（首次创建、以后 amend），保持 `讨论中`，保留工作树与主题分支 |
| 用户确认方案 | 状态改 `已定稿`、刷新日期、核对最后一个讨论阶段 → 同主题归档 → 按 reference §4 本地合入与清理 |
| 用户决定放下 | 状态改 `已搁置` + 原因 → 同主题归档 → 按 reference §4 本地合入与清理 |

**讨论中不反复合入主线**。本地存档不等于跨设备可用；需要远端同步时按 reference §3 核实授权与发布状态，已发布历史不暗中改写或强推。若归档、合入或清理受阻，报告文件所在绝对路径、分支及待处理项，保留现场，不追加同主题临时提交来绕过。

收尾到此为止：**不拆 issue、不碰 DEVTREE、不写 SUMMARY**。以后若要落地某部分，由用户自行 `/start`，并在该轮的 `PROMPT.md` / `PLAN.md` 里引用 `docs/design/<主题>/DESIGN.md`；design 这边**不反向维护**「被哪些轮用过」。

纯设计文档是否跳过 review 由 `/review-loop` 判定，资产或规则变更不能一概当纯文档；归档不带 `[round N]`，始终保留主题 trailer 与实际提交 Agent 的署名。
