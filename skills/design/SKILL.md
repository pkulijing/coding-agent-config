用户调用此 skill 表示手上有一段**还不清晰的背景**，想和你在讨论中逐步收敛出一个方案。**方案本身就是这一轮的最终产出** —— 它可能很宏观、未必落到可执行计划，以后可能拆成很多轮 `/start` 去做，也可能不做。

与现有开发流的分工：

| 入口 | 前提 | 产出 |
| --- | --- | --- |
| **`/design`** | 需求模糊，要讨论才知道做什么 | `docs/design/<主题>.md` 单文件 |
| `/start` → `/finish` | 需求明确，要开发 | 轮次记录 `docs/<N>-*.md` + 代码 |
| `/quick` | 小改，一句话说得清 | 仅 commit |

**明确不做**：不建 worktree、不建分支、不启动计划模式、不改业务代码、不拆 issue、不写轮次记录、不碰 `docs/DEVTREE.md`。所有文件写在**主 checkout**，收尾时直接提交（不带 `[round N]` 前缀）。

**入口守卫**：当前若在 linked worktree 内（比较 `git rev-parse --path-format=absolute --git-dir` 与 `--git-common-dir` 的绝对路径，不相等即在 linked worktree；不要直接比较两个相对输出）或分支匹配 `^(?:codex/)?round\d+`，停下提示用户「/design 不进轮次，请回主 checkout 运行」，不在轮分支上写设计文件。

## 参数

| 形态 | 行为 |
| --- | --- |
| `/design <背景描述>` | 新开一份讨论（见「开场」） |
| `/design --resume <主题>` | 定位已有 `docs/design/<主题>.md` 续聊；主题名模糊匹配，命中多个让用户选，无匹配则列出现有设计文件 |
| 无参数 | 列出现有设计文件及状态，问用户新开还是续聊；无主题则追问背景描述 |

## 开场

1. 从背景描述提炼简短**中文主题**，落点 `docs/design/<主题>.md`（**不带编号**）。已存在则确认续聊或换主题，绝不覆盖；跨会话长讨论才另加 `docs/design/<主题>-discussion.md` 记历史，该文件顶部同样要一行 `> 读者：<谁> · <什么问题>`，不需要状态行。
2. **先落盘再提问**：写骨架（状态 `讨论中`、各节暂空或写「待讨论」），顶部两行：

   ```markdown
   > 读者：要落地这个方案的人 · 当初为什么这么定
   > 状态：讨论中（YYYY-MM-DD）
   ```

3. 复述你对背景的理解（一两句），抛出第一轮问题。

## 讨论方法

- **阶段推进**：问题定义 → 约束与前提 → 方案空间 → 取舍 → 收敛成方案。这是默认路线而非死流程，可跳、可回退；**每个阶段收束时向用户确认一次**再往下走。
- **每轮只抛 1–2 个关键问题，每个都附你的建议与理由。** 不做开放式盘问，也不一次列一长串待确认项。用户说「听你的」就按建议定，照样记为决策。
- **引导，但不替人拍板**：方向性的取舍给出推荐并说明代价，由用户决定。
- **分清事实与判断**：能读代码、查资料确认的自己去查（**只读**），别拿来问用户；查不到、或属于「只有人知道」的参数（宪法·计划段）问人，不得猜。涉及外部权威材料的断言遵循宪法「先取原文」。
- **只写 `docs/design/` 下本主题的文件**（获授权的配图放同目录 `assets/`），不改业务代码或其他文档。讨论中冒出「顺手改一下」的冲动，记进「开放问题」或「分阶段路线」，不动手。

## 文件格式

```markdown
# <主题>

> 读者：<谁> · <什么问题>
> 状态：讨论中（YYYY-MM-DD）

## 目标与非目标
## 核心判断
## 方案框架
## 分阶段路线
## 开放问题
```

- 状态取值：`讨论中` / `已定稿` / `已搁置`；`已搁置` 时在状态行下补一行原因。
- 章节是建议骨架，**按主题增删**；「分阶段路线」对纯宏观讨论可以没有，不要求落到可执行粒度。
- 讨论中**整体改写**以反映当前共识，不追加历史流水；只有跨会话续聊时才用 `-discussion.md` 追加阶段记录。
- 读者只读这一份也要能看懂方案：写结论与理由，不写「见讨论记录阶段 3」式的跳转。

## 续聊

读 `docs/design/<主题>.md`（有 `-discussion.md` 一并读），向用户复述：当前共识（几句话）、开放问题、上次停在哪。然后从开放问题继续，并更新状态行里的日期。重开的是 `已定稿` / `已搁置` 方案时，状态改回 `讨论中`。

## 收尾与落地

| 时机 | 做法 |
| --- | --- |
| 一次会话结束、讨论未完 | 对齐文件、保持 `讨论中`，按 `/commit` 提交；不上 push |
| 用户确认方案 | 状态改 `已定稿`、更新状态行日期 → 提交 |
| 用户决定放下 | 状态改 `已搁置` + 原因 → 提交 |

提交走普通 `/commit`（纯文档可跳过 review-loop，由它自己判定），**不带 `[round N]` 前缀**，可在 message body 带 `Design-Topic: <主题>`。不 amend、不改写已发布历史；需要部署到远端时按实际授权处理。

收尾到此为止：**不拆 issue、不碰 DEVTREE、不写轮次记录**。以后落地某部分时由用户跑 `/start`，在轮次记录的「来源」行引用本文件；design 这边**不反向维护**「被哪些轮用过」。

新决策落地为实施轮之后，如果改变了本方案的结论，**在方案文件里直接改**（它是当前共识，不是历史档案）；确属需要保留的对抗性取舍，才在实施轮另写 ADR 并在本文件加一行链接。
