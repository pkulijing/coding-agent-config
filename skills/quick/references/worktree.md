# 轻量 worktree

供 `/quick --worktree` 与两条 routine 复用，仅处理隔离、路径与清理，不引入编号开发文档或授权远端操作。routine 保留自己的分诊、提交和 PR 契约，不整体调用 `/quick`，也不受 quick 的小改范围限制。

## 创建与锚定

1. 用 `git worktree list --porcelain` 与 `git rev-parse --git-common-dir` 核实主 checkout、当前真实路径和已有 worktree。主 checkout 只作为仓库入口：不要求它干净或处于默认分支，不切分支、不 merge、不 reset/clean、不提交，也不搬走其已有改动。记录启动时主 checkout 的分支和状态，结束时复核；若有其他会话变化，只报告，不替其恢复。
2. 普通 quick 默认从调用处 HEAD 创建；routine 必须先核实 origin 和远端默认分支，`git fetch origin` 成功后解析 `origin/<默认分支>` 的 SHA，以此固定基线；不更新本地主分支。同步或权限失败遵循调用方失败出口。已有托管工作树只有在确认属于本次运行、尚无任务改动且 HEAD 等于所需基线时才可复用；其他 linked worktree 保持原样，另建本次工作树，不在其内部嵌套创建。
3. 分支与入口用唯一新名：quick 为 `codex/quick/<ascii 短描述>`，routine 使用自己的 `auto/dev-…` / `auto/slim-…` 命名，入口把分支中的 `/` 换成 `-`。检查本地、远端同名分支及入口（含断链）；有占用就选新后缀，不覆盖、不强推。创建失败先核实是否已有部分成果，不盲目重试或删除。
4. 按 `~/.coding-agent/skills/start/references/worktree-create.md` 的「创建方式」「项目内入口」和依赖准备规则创建或复用；只取这些适用细则，不引入 round 编号、文档和计划确认。工具参数以当前实际 schema 为准。普通 Git 用 `git -C <主checkout> worktree add <主checkout>/.worktrees/<入口名> -b <分支> <基线SHA>`；托管工作树保留应用返回的真实路径，在项目 `.worktrees/` 建入口，并在真实路径创建分支。没有托管工具的环境用普通 Git；托管创建调用失败则报告并停止，不能把部分创建状态当作未创建。
5. 创建后核对真实路径、分支、HEAD 与干净状态；目录级忽略和项目内入口必须验证就绪。此后所有读取、修改、验证、review、提交和 PR 操作显式锚定该真实绝对路径；子 agent 也接收同一路径。不要因全局技能软链指向主 checkout 而改写或审错工作树：调用方要求起始基线的资源从固定 SHA 读取。

## 保留与清理

- 普通 quick 提交后默认保留 worktree 和分支，输出路径与 SHA 等待审阅；用户授权提 PR 就按授权执行，不自动合入。
- routine 成功创建并回读确认 PR 后，核实工作树干净、远端 PR head 等于本地 HEAD，才能清理本次工作树；本地与远端分支保留供 PR 审阅，不更新主 checkout。移除前将后续命令的工作目录设为主 checkout，只在那里执行带明确目标的生命周期命令。
- 普通 Git 用 `git worktree remove <本次真实路径>`；托管工作树用所属应用 archive，确认成功后仅移除仍指向该真实路径的本次软链接。不用 `--force`、递归删除或普通 Git 删除托管目录。归档附带会话状态变更时按工具实际语义报告。
- push / 开 PR 失败、有未提交/未跟踪文件、未推送提交或资产归属不明时，保留工作树和分支并报告路径、SHA、远端资产及恢复方式；不为让主 checkout 看起来干净而删除成果。显式放弃的 routine 空分支/失败批次，只有已确认全属本次且无需保全时才按调用方检查点清理，再移除该工作树与本次未推送分支；已推送分支不删除。
- 最后复核主 checkout 的分支和状态，报告它是否与启动时一致；不要求或假报主 checkout 一定干净。用户已有脏改动必须原样保留。

## 本机调度入口

从云端新 clone 迁到本机时，两条 routine 的调度 Prompt 只保留仓库、技能与权限申请入口；工作区前置闸以本技能的独立 worktree 契约为准。移除旧 Prompt 中“当前主 checkout 必须干净/处于默认分支”“分支不符中止”“结束回默认分支”等覆盖技能的要求。排期、模型与平台审批机制不随此变更。仓库规则与已有调度 Prompt 分开部署；规则尚未合入时不把它描述为已生效，部署后回读配置确认。
