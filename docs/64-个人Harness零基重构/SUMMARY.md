# 个人 Harness 零基重构

## 开发项背景

规则长期由事故和补丁单向积累。全局入口包含技能细节，领域文档把项目/SDK特例默认扩展到整类任务，finish 持续寻找全局候选，routine-slim 又禁止真正退役，增加了用户与 Agent 的维护负担。

本轮按用户确认的零基尺度整理，目标是减少用户介入，保留自主执行能力，不建设评测项目。

## 实现方案

- 全局保留个人偏好、协作与授权边界、必要资源/结果核验，删除事故叙事和重复操作细节；README 改为使用入口与维护说明。
- 十份 playbook 改为短领域入口，仅保留三个按实际场景加载的 reference。删除旧模型成绩、项目特例配方和泛化禁令；未另建事故档案。
- skills 清理重复与漂移，保留已有流程、命令开关、review 编队/角度/模型/思考档及失败出口。模板合并协议继续作为单一真源。
- finish 只有能说明跨项目收益的候选才提出沉淀，无候选不再制造“暂无”栏目或询问。跨仓发布仍需原有确认。
- routine-slim 每次有界盘点，允许普通旧规则退役，不再要求增长超过15%或所有删除信息另有存放处；保留1–3文件、原权限、在途PR排除、基线审查和人工合入。
- 修正环境参数语义、前端配置说明及旧review出口；去掉WebGL目录的Hook检查豁免。私服与ROS安装说明不再默认绕过TLS或把token写入依赖文件。
- helper 增加 issue-close，原生关闭后回查状态与GitHub关闭原因；引用检查器兼容playbook reference，历史token估算标明非当前实测。

验证记录见 VALIDATION.md 及专项记录；独立审查按起始版本执行，结果见 REVIEW.md。

## 局限性

静态审查与隔离测试不能证明模型质量不会下降。没有运行真实远端关闭操作，没有重新部署或实跑云端routine，也没有变更hook信任。当前会话不保证热加载新规则，合入后用新会话进入日常开发。

新增领域reference不在routine原写白名单内，本轮没有扩权；它们后续由明确授权的开发轮维护。只有出现反复、具体的问题才局部补回规则，不恢复默认事故升级机制。

## 后续 TODO

新版进入日常开发后，只在反复出现具体问题时局部补回。无需用户维护基准、题库或新指标。lint失败交互策略、review编队经济性、自动化平台迁移不在本轮内。

用户在计划确认后进一步授权自主完成本轮收尾。本轮据此完成本地提交与合入，不推送远端；未来技能中的确认边界不因此改变。

## 回退与部署

开发分支为 `round64-harness-reset`，起始版本为 `1e5cb3e5da49bea7195ab472c070167c92e70c0b`。保留 `backup/round64-harness-baseline` 指向该版本。合入前复核主线仍处于此 SHA，无需处理并行冲突。

本轮实现以单个 `[round 64] refactor(harness)` 提交交付；用 `git log --oneline --grep="\[round 64\] refactor(harness)"` 定位，再对该 SHA 执行 `git revert <SHA>`，保留其他后续提交。不reset共享历史，不把全局链接改向临时工作树。普通目录软链内容随主checkout变化生效；若回退涉及技能发现增删或原生配置，再从主checkout运行安装。本轮未增删技能或更改原生配置基线，不需要因三个领域reference新增而重装。
