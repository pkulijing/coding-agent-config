# 个人 Harness 零基重构计划

状态：用户已于 2026-11-06 确认，按本计划实施。审查使用起始基线，不使用改写后的标准放行自身。

## 关键设计决策

目标是降低用户维护与纠正成本。以实际任务的加载路径和行为契约组织内容，不按字数配额，也不维护逐句规则资产库。

1. **全局入口**只承载个人偏好、协作与授权边界、保护资产和结果诚实的必要规则，以及可判别的领域/技能路由。TDD 等明确工作方式保留简短契约，通用编程教程退出。
2. **领域入口**保留该领域的个人选择；SDK、发布渠道、异步服务、进程管理等只在对应操作时加载。先删除无持续价值内容，仍需细节才使用 reference，避免拆出一批必读小文件。
3. **技能**直接表达输入、产出、判断条件和失败出口。流程只有一个权威正文，调用方只保留路由所需信息。保持现有自动化能力、确认边界与命令开关语义。
4. **代码、模板与文案一起核对**。规则不再复述模板参数，引用实际配置；若发现行为本身有问题，最小修复并测试，不能仅删说明掩盖问题。
5. **历史不搬家**。旧 docs 与 Git 保持原貌，本轮只记录关键取舍、验证和最终行为变化，不建逐条迁移账本。

## 实施顺序与范围

### 1. 固定检查基线，整理全局入口

- 使用起始 SHA `1e5cb3e5da49bea7195ab472c070167c92e70c0b` 的 review-loop、angles、agents、commit/lint 规则执行本轮审查。用 Git 读取指定版本，必要时物化到临时只读审查目录；不从修改中的工作树或后来变化的全局软链取审查标准。
- 改 GLOBAL_AGENTS.md 与 AGENTS.md，建立偏好/边界到最终落点的简短验收表；这张表仅是本轮审查材料，不成为长期规则登记框架。
- 本轮可以修改 routine 的指令，因为用户明确要求重构这些机制；不以 routine 自身白名单限制人类发起的本轮，也不扩大未来 routine 的文件权限。

### 2. 按任务整理 playbooks 与 skills

- 全量审阅当前托管 playbooks、skills 正文及实际引用，逐段自主决定删除、收窄或重写。优先处理 python、shell、llm-app，以及 start/finish/commit/rebase/review-loop 的重复契约。
- 保留 uv/npm/Biome、布局与风格等现有明确个人默认值，压缩说明；不因主观判断“常识”取消偏好。版本特例优先交给实际项目配置，技术事实查证后再写。
- references 的入口同时写清触发条件，不要求先读完整 reference 才能判断是否该读；无关任务不递归遍历。
- 核对 bootstrap/sync、templates/MECHANICS.md、agent 任务书、README 的接壤副本。agent 模型/思考档、review 人数、角度覆盖、降级门槛和两轮规则不变。
- 不批量修改历史 docs，不修改其他业务项目、第三方安装技能或凭据配置，不迁移自动化平台。

### 3. 改规则进入与退出机制

- **finish**：默认把修复放在来源项目实现、测试或文档；只有现有工具/规则不能覆盖且能说明跨项目收益时才形成候选。候选写清适用条件、具体落点、为何不能留在本地；取消无候选时的强制“暂无”栏目。不要求用户每轮寻找沉淀机会。跨仓 issue 仍遵循既有确认与三轴标签规则，不自动发布。
- **routine-slim**：保留现有周期、1–3 文件批次、在途 PR 排除、文件白黑名单、PR 人工合入与远端写操作边界；允许退役普通指令，不再要求所有旧信息能从别处读到。PR 简述删掉什么、为何不再需要、影响哪些行为；只有搬移才要求新落点。
- **触发建议**：取消增长 15% 作为唯一启动条件，每次定时执行有界盘点；优先最近变更与明显重复/过宽项，没有值得做的候选就退出。沿用 Git 历史，不建状态服务或候选数据库。字符数可作辅助描述，不作为启动必要条件或验收。
- 安全边界、个人偏好与工作流能力不属于 routine 可自行退役的对象。它不能借删除改掉 reviewer 数量、授权或交付方式；本次检查使用起始基线，未来改规则的任务同样按其起始基线检查。
- routine 仍只基于仓库材料作业；需要外部证据才能判断的技术删除，不把未查证当成过期理由。已有 Git/issue 证据足够时可退役，否则保留并说明，不扩大其联网/远端权限。

### 4. 修复真实漂移并完成验证

- finish 的 issue 关闭路径目前缺少 helper 能力：计划最小补齐 `issue-close`，沿用 helper 的平台分流与失败模型。先核实两端原生关闭参数，再写 GitHub/GitLab 命令构造、关闭原因与失败传播测试，最后实现和同步接口说明；不顺带重构 helper。
- 其他脚本/模板行为仅在证据表明是本轮规则清理不可分割的错误时修复；需要改变个人选择或扩大交付范围时集中报告。
- README 改成现行入口与维护方式；按原流程维护 DEVTREE、提交、最终 SUMMARY。计划确认前不提前执行。

| 触发连贯性 | 静态沿调用链检查普通 Python 改动、发布、LLM 文本调用、流式调用、start→commit→finish、两条 routine 的入口和异常出口。仅作路径核对，不运行多模型任务或建设题库 |
| 技术断言 | 查本机源代码/CLI 帮助/官方原文，必要时临时最小探针；记录与最终改动有关的结论。取不到不伪称已验证，也不以未验证为退役证据 |
| 脚本与配置 | 改 helper 则先红后绿、平台自检和受影响测试；改模板则跑对应解析/lint/构建验证；涉及安装映射则用既有临时 HOME 沙盘，禁止在 linked worktree 安装 |
| 独立 review | 每个开发单元按基线 commit/review 规范；跨入口编排按原复杂度规则选档，保留全部角度与模型配置。最终审查整体 diff 的规则遗漏、越权和引用闭环；失败/降级如实留痕 |

完成时交付可用版本、简短删减与保留说明、行为变化及验证局限。不把静态审查通过描述为模型质量保证；不新增评测基建或用户维护任务。

## 发布与回退

- 实施在隔离工作树，主 checkout 的已部署规则在合入前保持原版。review 基线 SHA 固定不随主分支变化。
- 最终使用既有 finish 流程；合入前保留明确的基线 tag，并在 SUMMARY 列本轮提交集合。若主分支届时前进，另记录实际合入前 SHA，不把今天的基线冒充最终回退点。
- 回退采用对本轮提交的逆序 revert，保留后来工作和直线历史；不 reset 远端、不把部署软链指向临时工作树。新增/删除技能或配置基线变化后，从主 checkout 运行安装，其他目录软链内容随合入生效。
- 若涉及 hook 配置，仍由用户完成原有信任审阅；本轮不默认修改 hook 信任或调度注册。新会话使用新版，现有会话不宣称已热更新。
