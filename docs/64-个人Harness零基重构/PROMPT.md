# 个人 Harness 零基重构

## 需求来源与目标

用户于 2026-11-06 发起专题：清理 coding-agent-config 随旧模型、历史事故和反复补丁累积的指令负担，重新形成适合个人使用的 harness。优化目标是减少用户操心、纠正和维护的时间，同时让 Agent 自主完成工作。token 和运行时间属于成本，但能减少用户介入的后台自动化值得保留。

本轮先完成现状分析与具体计划，等用户确认后实施；用户确认尺度，不逐条裁决规则。只有影响个人偏好、授权边界或交付方式的取舍需要集中确认。

## 已决范围

- 从当前工作需要出发，旧规则及事故不自动构成保留理由；篇幅长或流程复杂也不自动构成删除理由。
- 保留语言、Git、提交署名、issue 管理等明确偏好，需求—计划—执行—总结流程与方向性取舍确认边界。
- 保留 worktree 隔离、自动提交、独立 review 等自动化；保护已有工作、权限和凭据，避免误报成功；保留无法从代码推知的环境事实和有效特殊限制。
- 清理宪法中的通用说教、重复定义、事故长篇叙事；收窄 playbooks 里项目、SDK、版本和部署条件特有的规则；整理 skills 重复流程和漂移副本。
- 核实技术断言，修正错误、矛盾、过期参数与失效引用；调整 finish 的跨项目沉淀、routine-slim 的只搬移不淘汰机制。
- 规则直接表达条件与行为，必要理由简短保留；一次性经验优先留在来源项目测试或文档。历史已有 Git/issue 可追溯时不另造档案。
- references 只在实际相关时加载，不以“拿不准全读”恢复全文加载；无预设删减比例或字符数验收指标。
- 不默认减少 reviewer、取消文档流程、改变权限；其他工作流重构仅列建议。
- 优先复用工具，不为删提示另建复杂框架。

## 验证与交付

检查入口、引用、技能依赖与触发条件的连贯性，保留明确偏好和关键边界。按修改前审查标准 review；脚本或配置行为修改执行相应验证。

不建设基准题库，不要求用户做 A/B、消融实验或多模型重复任务。静态审查只报告其可证明的结果，不宣称模型质量不会下降；新版通过后用于日常开发，反复出现具体问题再局部补回。

最终交付可继续使用的配置与指令、简短变化说明、明确回退方式，以及避免事故默认升级为全局规则的进入/退出机制。
