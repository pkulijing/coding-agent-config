# 放宽自动化开发接单范围

## 开发项背景

用户确认，既有自动开发 MR 合入后不需要人工修改或返工，但文档自动通道和逐条授权让明确的 skill、模板及代码改进长期滞留。本轮扩大自动化开发范围，由 MR 承载结果和人工合入决策。

## 实现方案

统一 routine-dev 接单：取消逐条授权和 P0 拒收，允许常规 skill、模板、脚本、hook 及文档修改；目标未收敛的开放讨论拒收，新增 `status:discussion` 表达这一状态。多文件任务和实现选型由 Agent 自主完成，环境缺项须实际核验。

routine 自主计划、实现、验证并调用 commit，不再依赖 quick 的轻量定位。完整交付才自动关闭 issue；部分交付须独立有价值、如实标注。复核起始基线的 review 规则，提 PR 前重新检查 issue 状态、真实落点、红线及在途 PR。保留一次一个 PR、最多三次尝试和人工合入。

同步安全推导、AGENTS、README、triage 和 routine-slim 的引用说明。公开文本不授权外部写操作，文字禁令与凭证隔离明确区分。#145 的旧候选授权入口问题由统一接单吸收。#66 的案例数量前置条件取消决定已回写，且回查 ownerHint 确认可读。

候选规则下全量静态分诊取得 18 条 open issue：14 条可进入候选、4 条拒收；#121 实验环境仍待实际核验。具体案例、限制及验证方法见 DRY-RUN.md。引用检查、YAML/frontmatter 结构检查和 diff 空白检查通过，独立审查见 REVIEW.md。

## 局限性

- 本轮按候选规则只读分诊，没有在真实调度器执行一次完整自动开发，也未验证 #121 的日志、用量和对照实验条件。
- 未部署独立身份或凭证隔离；owner 身份无法区分人和 Agent 的限制仍在，远端写操作靠必须遵守的流程约束限制。
- 零 PR 输出仍无新增持久通知通道；稳定排序与三次失败上限仍可能阻塞后续候选。
- 新标签待定义合入后同步，#39 的显式讨论标签设置随之执行；正文判定在没有该标签时仍必须拒收开放讨论。
- #7、#99 已有 wontfix，但 helper 缺关闭子命令、连接器关闭返回 403，尚未完成关闭；本轮不扩展 helper。
