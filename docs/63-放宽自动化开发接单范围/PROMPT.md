# 放宽自动化开发接单范围

## 背景

用户确认，迄今自动化开发提交并合入的 MR 没有需要人工修改或事后返工的情况。现有 `/routine-dev` 通过“只允许文档的自动通道 + 逐条打 `auto:take` 的标记通道”接单，导致不少目标明确的需求长期滞留；用户没有足够时间逐条审阅并打授权标签，希望明显放宽自动化开发范围。

2026-11-04 的只读盘点取得 17 条 open issue，均未带 `auto:take`；当时没有 open PR，本地主线与远端一致。按当时规则，16 条会被过滤，只有 #154 的预期落点属于自动通道白名单。这是静态规则复核，不是历史运行日志分析。

## 用户已确认的方向

1. 取消 `auto:take` 逐条授权机制，常规 skill、模板、脚本和 hook 修改可以自动接单。
2. `priority:P0` 不是合理的排除因素；优先级用于排序。
3. 需求目标尚未收敛的开放讨论类 issue 明确禁止自动开发，#39 是代表案例。
4. “目标明确、实现方案未选定”不等于开放讨论。Agent 可以自主调研、选择实现方案、验证后提交 MR；此前列为疑问的 #160、#121 等不因方案未定而一概排除。
5. #66 做不做都可以，不再用旧正文中“等第二次案例”的条件将它永久挡住。
6. #7、#99 已决定不做，应归档关闭。此前已通过 helper 添加 `wontfix`，关闭状态的连接器调用均返回 403，尚未完成关闭。
7. #121 可能受实验环境限制。应在实际检查所需日志、用量数据及对照实验条件后判断，不能凭推测断言不可做，不能用估算替代实测。

## 本轮目标

将上述方向落实到 `/routine-dev` 的接单、开发、验证和报告规则，并同步受影响的现行文档与标签定义。自动化的主要工作是自主完成目标明确的开发任务，由 MR 承载结果和人工合入决策。

现行四条红线、合入权限与外部副作用不因取消 `auto:take` 自动放宽。本轮由人在环明确发起修改 routine 本身，不能被后续无人值守运行解释为持续自改授权。

## 范围与边界

- 包含 routine-dev 主流程和安全推导、triage 的自动化状态说明、routine-slim 中引用旧双通道授权的段落、README、本仓 AGENTS 和标签定义。
- 本轮不顺带实现上述积压 issue 的业务改动；#145 的旧授权入口问题由本轮新机制吸收。
- 不引入自动合入，不修改合入 workflow，不调整 reviewer 模型、思考档或强度。
- 不重写历史开发记录，不把本次 issue 盘点变成长期本地索引。

## 验收要求

- 明确需求无需 `auto:take` 即可进入开发，P0 可被正常选择。
- #39 这样的开放讨论可以显式标识并被拒收；#160 这样的明确目标不因实现方案选择而误判为讨论。
- 多文件、需要验证的任务不再因超出 `/quick` 的轻量定位被拒收，也不无人值守等待计划确认。
- 环境不足有实际证据、具体缺项和明确处理动作，不能伪造已完成、测试通过或实测结论。
- 规则、安全推导、发现入口和 README 一致，提交前完成独立 context review 及适当验证。
